  \end{tikzpicture}\par\endgroup
  \vskip 0.3em
  \small
  \begin{itemize}
    \item The answer depends on the task. A thermostat needs one reading
          each few minutes. A machine that can break needs several readings
          each second.
    \item Three questions: how fast does the value change? How fast must the
          receiver act? What does one message cost in bytes and energy?
    \item Sample fast, send slow. The sampling rate (Day 2) is not the
          reporting rate. The device can read each second and send each
          minute.
    \item \textbf{On change}: send when the value moves more than a band,
          and a heartbeat after a fixed time with no message. The receiver
          then knows that the device is alive.
  \end{itemize}
\end{frame}

\begin{frame}{A lost link: three choices}
  \footnotesize
  \renewcommand{\arraystretch}{1.2}
  \setlength{\tabcolsep}{4pt}
  \begin{tabular}{@{}L{2.4cm}L{3.6cm}L{4.0cm}@{}}
    \toprule
    \textbf{Choice} & \textbf{When} & \textbf{Example} \\
    \midrule
    Drop & only the newest value matters & the temperature for a
      thermostat \\
    Keep the newest & a state or a setting & a retained status, a
      threshold \\
    Store and forward & each message matters & counts, events, the data of
      a trend \\
    \bottomrule
  \end{tabular}
  \vskip 0.5em
  \small
  \begin{itemize}
    \item A heating system does not need the temperature of 20 minutes ago.
          A model that looks for a change in a trend needs each value.
    \item Commands to a device that is away: drop the old ones, or keep only
          the newest. Commands that must run in order need a queue with
          sequence numbers.
    \item The local decisions continue in all three cases (Part 1). Only
          the messages to the cloud wait.
  \end{itemize}
\end{frame}

    \node[b, text width=1.4cm] (c) at (7.0,0) {Cloud broker};
    \node[b, text width=1.1cm] (r) at (9.0,0) {Receiver};
    \draw[->] (x) -- (l);
    \draw[->] (l) -- (f);
    \draw[->] (f) -- node[above] {QoS 1} (c);
    \draw[->] (c) -- (r);
    \node[cardinalred, font=\normalsize] at (5.7,-0.3) {$\times$};
    \node[below, align=center] at (4.2,-0.85) {1. write\quad 2. send the
      oldest\quad 3. delete after the PUBACK};
  \end{tikzpicture}\par\endgroup
  \vskip 0.4em
  \small
  \begin{itemize}
    \item Write each message to the queue before you send it. Delete it
          only after the PUBACK of the cloud broker.
    \item A message with no PUBACK is sent again: the receiver can get two
          copies. It keeps the pair (device, \code{seq}) and drops a second
          copy.
    \item After a long cut, the receiver gets old messages. It uses the time
          stamp of the device, not the time of arrival.
    \item The queue must be on disk, not only in memory: the device can
          restart during the cut.
  \end{itemize}
\end{frame}

\begin{frame}{Measured: two traps of a queue on disk}
  \small
  \textbf{1. Each commit waits for the disk.}
  \vskip 0.2em
  \footnotesize
  \renewcommand{\arraystretch}{1.12}
  \begin{tabular}{@{}L{5.6cm}rr@{}}
    \toprule
    \textbf{SQLite, one INSERT and one commit} & \textbf{Median} &
      \textbf{p95} \\
    \midrule
    Default settings & 2.8 ms & 3.9 ms \\
    \code{journal\_mode=WAL}, \code{synchronous=NORMAL} & 0.027 ms &
      0.035 ms \\
    \bottomrule
  \end{tabular}
  \vskip 0.3em
  \small
  \begin{itemize}
    \item With the defaults, the queue writes at most about 350
          messages each second on this disk. A microSD card is slower.
  \end{itemize}
  \vskip 0.3em
  \textbf{2. A new row can get the ID of a deleted row.}
  \begin{itemize}
    \item The first forwarder of this experiment marked the sent rows by
          their ID. SQLite gave new messages the IDs of deleted ones: 1160
          of 1200 messages were never sent.
    \item Use \code{AUTOINCREMENT}, or a column ``sent'' in the row.
  \end{itemize}
  \keypoint{Test the buffer with a real cut of the link, and count each
    message at the receiver.}
  \source{Experiment of this course (200 commits for each setting).}
\end{frame}

\begin{frame}[fragile]{A Mosquitto bridge on the Raspberry Pi}
\begin{lstlisting}[style=shell]
# /etc/mosquitto/conf.d/bridge.conf on pi-07
connection cloud
address 192.168.8.10:1883
topic edgeai/g07/# out 1
cleansession false
remote_clientid pi-07-bridge
max_queued_messages 100000
persistence true
\end{lstlisting}
  \small
  \begin{itemize}
    \item The bridge is a client of the cloud broker. It sends each local
          message of \code{edgeai/g07/\#} with QoS 1 (\code{out}: only
          from the Pi to the cloud).
    \item With \code{cleansession false}, the cloud broker keeps the
          session of the bridge during a cut.
    \item \code{max\_queued\_messages} is 1000 by default. Set it from the
          longest cut that you plan for.
    \item With \code{persistence true}, Mosquitto saves its queue to a file
          when it stops and each 30 minutes. A power cut loses the newest
          messages.
  \end{itemize}
  \source{Mosquitto 2.0.11 manual (\texttt{mosquitto.conf}). Address of the
    instructor laptop: hardware folder HW-09.}
\end{frame}

% ------------------------------------------------------------------ buffer size
\begin{frame}{Size the buffer}
  \small
  \[
    \text{buffer} = \text{messages each second} \times \text{longest cut}
      \times \text{bytes of one message}
  \]
  \vskip 0.2em
  \footnotesize
  \renewcommand{\arraystretch}{1.15}
  \begin{tabular}{@{}L{3.6cm}L{2.6cm}r@{}}
    \toprule
    \textbf{Device} & \textbf{Rate and cut} & \textbf{Buffer} \\
    \midrule
    XIAO, results & 2 each s, 10 minutes & 1200 $\times$ 60 B = 72 kB \\
    Raspberry Pi, detections & 10 each s, 1 day & 864\,000 $\times$ 100 B
      = 86.4 MB \\
    \bottomrule
  \end{tabular}
  \vskip 0.1em
  {\scriptsize Example values of this course. 1 kB = 1000 bytes.\par}
  \vskip 0.4em
  \small
  \begin{itemize}
    \item The Raspberry Pi has a microSD card of many GB: one day is easy.
          The XIAO has 8 MB of PSRAM: some minutes of results, or a summary.
    \item When the buffer is full, select a rule: drop the oldest, drop the
          newest, keep one message of each N, or keep only summaries.
    \item Flash memory wears with each write: write the queue in blocks, not
          one message at a time.
  \end{itemize}
\end{frame}

% ------------------------------------------------------------------ clocks
\begin{frame}{Time: three clocks}
  \footnotesize
  \renewcommand{\arraystretch}{1.2}
  \setlength{\tabcolsep}{4pt}
  \begin{tabular}{@{}L{2.5cm}L{2.7cm}L{4.8cm}@{}}
    \toprule
    \textbf{Clock} & \textbf{Example} & \textbf{Property} \\
    \midrule
    Time since boot & \code{millis()}, \code{time.monotonic()} & never
      jumps; starts at 0 after each restart \\
    Clock time (UTC) & \code{time.time()} & needs a synchronization; can
      jump when it is set \\
    Arrival time & the clock of the server & adds the network delay and the
      time in a buffer \\
    \bottomrule
  \end{tabular}
  \vskip 0.5em
  \small
  \begin{itemize}
    \item Put the time stamp on the message at the source, when the value is
          measured. After a cut, the arrival time can be minutes late.
    \item Use UTC in milliseconds: no time zones, no summer time.
    \item Measure a duration with the time since boot (Part 1). Name an
          instant with the clock time.
    \item Order the messages of one device by \code{seq}. A clock that jumps
          does not change this order.
  \end{itemize}
\end{frame}

    \begin{column}{0.56\textwidth}
      \small
      \[ \text{offset} = \frac{(t_2 - t_1) + (t_3 - t_4)}{2} \]
      \[ \text{delay} = (t_4 - t_1) - (t_3 - t_2) \]
    \end{column}
  \end{columns}
  \vskip 0.4em
  \small
  \begin{itemize}
    \item The formulas assume the same time in the two directions. The
          error of the offset is at most half of the delay.
    \item Measured: 10 requests from the work computer to
          \code{pool.ntp.org}: delay 68 to 98 ms, offset 0.2 to
          5.1 ms. Its clock was within some ms of the server.
    \item A device asks again at intervals, because its clock drifts. A
          clock with an error of 20 ppm (parts per million) drifts 1.7 s
          each day.
  \end{itemize}
  \source{RFC 5905 (NTP version 4), section 8. Measured by this course.}
\end{frame}

% ------------------------------------------------------------------ offline time
\begin{frame}{Time with no internet}
  \small
  \begin{itemize}
    \item In the lab, the internet link can fail. Then no device reaches
          \code{pool.ntp.org}.
    \item The Raspberry Pi is the time server of its group: \code{chrony}
          with the lines \code{allow 192.168.8.0/24} and
          \code{local stratum 10} serves its clock to the lab network.
    \item The Raspberry Pi 5 has a real-time clock. With a battery on the
          connector J5, it keeps the time with no power.
    \item The XIAO asks the Raspberry Pi at the start and each hour:
          \code{configTime(0, 0, "192.168.8.107")}.
    \item The XIAO has no battery for its clock. After a restart, it has no
          clock time until the first answer.
    \item Until then, the device sends \code{ms} since the start and a boot
          counter, and it marks the message ``not synchronized''. The
          receiver can then calculate the time from a later message.
  \end{itemize}
  \source{Raspberry Pi documentation, ``Real Time Clock (RTC)''. Addresses
    from the hardware folder HW-09.}
\end{frame}

% ------------------------------------------------------------------ identity
\begin{frame}[fragile]{Device identity}
  \small
  \begin{itemize}
    \item Each device has one ID that does not change: the MAC address in
          the eFuse of the ESP32-S3 (\code{ESP.getEfuseMac()}), the serial
          number of the Raspberry Pi.
    \item The same ID is in the client ID, in the topic, and in the status.
          A copied firmware must not copy the ID.
    \item Each device or group has its own password. The broker then limits
          each one to its own topics:
  \end{itemize}
\begin{lstlisting}[style=shell]
# Mosquitto ACL file: user g07 can use only edgeai/g07/...
pattern readwrite edgeai/%u/#
\end{lstlisting}
  \begin{itemize}
    \item The retained status names the device and its versions, so the
          server knows which model gave each result:
  \end{itemize}
\begin{lstlisting}[style=python]
{"id":"xiao-34851a2b3c4d","fw":"1.2.0","model":"kws-3","boot":17}
\end{lstlisting}
  \source{Mosquitto 2.0.11 manual (ACL patterns). Module SY-2 adds the
    passwords and TLS.}
\end{frame}

\exerciseframe{the data of one camera for a day}{%
  \small
  A camera node on a Raspberry Pi runs a person detector at 10 frames each
  second. Calculate the data that it sends in one day (86\,400 s) for each
  design:
  \begin{enumerate}
    \item The H.264 video stream at 2 Mbit/s.
    \item One result message for each processed frame. One message is 150
          bytes with all headers.
    \item One message only when the number of persons changes: 200 changes
          in one day, 150 bytes each.
  \end{enumerate}
  Give each result in bytes, and the ratio of design 1 to designs 2 and 3.
  Which design would you select for a dashboard of the people in a room?
  \vskip 0.3em
  Use 1 GB = 10\textsuperscript{9}
  bytes.
}

\begin{frame}{Answer: the data of one camera for a day}
  \footnotesize
  \renewcommand{\arraystretch}{1.2}
  \begin{tabular}{@{}L{3.0cm}L{4.4cm}r@{}}
    \toprule
    \textbf{Design} & \textbf{Calculation} & \textbf{One day} \\
    \midrule
    1. H.264 video & 2\,000\,000 / 8 $\times$ 86\,400 & 21.6 GB \\
    2. A result each frame & 10 $\times$ 150 $\times$ 86\,400 & 129.6 MB \\
    3. Only the changes & 200 $\times$ 150 & 30 kB \\
    \bottomrule
  \end{tabular}
  \vskip 0.5em
  \small
  \begin{itemize}
    \item Design 1 sends 167 times the data of design 2, and 720\,000 times
          the data of design 3.
    \item For a dashboard of the people in a room, design 3 is enough: add a
          heartbeat, so the dashboard knows that the node is alive.
    \item Keep design 2 for a short test, and a few images for a check by a
          person. The video stays on the node.
  \end{itemize}
\end{frame}
